# Astro 生态、主题与个人站点总览

核查日期：2026-11-08。本文合并 Astro 版本升级、部署、主题、个人站点和 Off by One 交互图表调研，作为后续主题选型的唯一维护入口。目标内容是论文笔记与周报：多图、公式、代码、表格，以及少量解释性互动。

## 1. 结论

当前有三条可行路线：

1. **AstroPaper 路线**：社区和维护信号最强，保留简洁文章页与 MDX，再接入论文卡片、图片灯箱和局部交互。
2. **astro-erudite 路线**：最接近 nightxade 与 Off by One 的长文视觉，但当前 v2 默认不带 MDX / React；需要验证交互组件接入。
3. **Axi Theme 路线**：合集、论文卡片、目录进度和 KaTeX 最贴近当前内容模型，但 stars 少、更新间隔较长，长期维护更依赖作者。

综合长期维护与论文内容，建议先用 AstroPaper 做稳定性对照，再用 erudite 和 Axi 做视觉及信息架构对照。主题只负责页面和 Markdown 体验；交互图表应作为独立组件接入，不应为了一个图表替换整站。

## 2. Astro 框架与部署

核查时 Astro 最新稳定版为 7.4.7。Astro 7 的方向集中在 Vite 8 / Rolldown、Rust 编译器与 Markdown / MDX 处理、内容集合、构建性能、缓存和部署诊断。7.2 的增量静态构建、7.4 的并行预渲染等能力仍需按官方标记评估，不能把实验功能当成生产前提。[^astro-latest][^astro-v7]

Astro 7 默认使用 Sätteri Markdown 处理器。现有 `remark-math`、`rehype-katex` 和自定义插件可以继续通过 unified 管线使用，但公式解析、渲染结果和主题 CSS 需要逐项检查。不同主题声明的 Astro 版本差异很大，不能安装主题后直接运行升级命令。

GitHub Pages 可以承载静态 Astro 站点。Markdown / MDX、公式、目录、图片放大、Mermaid 和 React islands 都可以在构建后部署；登录、数据库写入、请求时服务端代码和 Astro Actions 需要外部运行环境。用户站 `WncFht.github.io` 属于根路径站点，不需要项目名 `base`；Astro 默认构建目录为 `dist/`。[^github-pages]

## 5. Feature 实现方案比较

主题提供的是一组默认页面和内容管线。同一个 feature 可以由主题内置、Astro 插件、Markdown 插件或客户端 island 实现。下面按论文笔记和论文周报的实际使用顺序比较方案。

### 5.1 页面结构

#### 首页

首页通常有三种结构：

| 结构 | 主要内容 | 优点 | 代价 |
| --- | --- | --- | --- |
| 文章列表型 | 最近文章、日期、摘要、阅读时间、分页 | 维护简单，文章多时仍清晰 | 专题和论文成果需要额外入口 |
| 专题入口型 | Agent、论文周报、Publications、项目、最近文章 | 研究方向清楚，减少 tag 维护 | 首页信息密度更高，需要维护专题元数据 |
| 个人主页型 | 个人简介、项目、外部链接，博客作为一个模块 | 个人品牌和项目展示自然 | 长期写作的内容发现效率较低 |

本站适合“个人介绍 + 专题入口 + 最近文章”的组合。专题使用少量固定字段，例如 `collection: agent` 和 `kind: paper-weekly`，不恢复大量 tag。

#### 文章页

论文长文建议采用桌面端“文章信息 / 正文 / 固定目录”布局，移动端将目录折叠为按钮。页面至少需要标题、摘要、日期、文章类型、阅读时间、目录、正文、参考文献、同专题文章和前后篇导航。

文章内容可以保持独立 URL，例如 `/weekly/2026-w45`。erudite 的 Subposts 连续长文适合教程或一篇长期维护的综述，不适合把所有周报拼成一个无限增长的页面。

#### 专题页

专题页建议包含专题简介、文章数量、最近更新时间和文章列表。实现上可以选择手动 slug 列表，或在 frontmatter 中写固定的 `collection` 字段。后者更适合文章数量增长后的自动生成；前者更适合严格控制专题顺序。

### 5.2 阅读与内容

#### 字体与正文密度

当前字体计划可以保持：中文使用 LXGW WenKai Screen，代码使用 JetBrains Mono。JetBrains Mono 更适合代码和标题，不建议直接作为长篇英文正文；英文正文可以用 Inter、IBM Plex Sans 或 Source Serif，公式使用 KaTeX / MathML 自己的数学字体。

文章正文需要稳定的最大宽度、行高、标题间距、引用样式和窄屏边距。论文页面优先保证公式、图片和表格不撑破正文，再处理装饰。

#### 目录与进度

目录实现可以分为三档：

1. 普通目录：只生成标题链接，最稳定，无 JavaScript 也能使用。
2. Scrollspy：使用 `IntersectionObserver` 高亮当前标题，适合长文定位。
3. 目录 + 分节进度：在高亮基础上标记已读章节或当前章节进度，Axi Theme 的实现值得参考。

本站建议桌面端固定右侧目录、移动端顶部目录按钮，并只保留一个全文阅读进度提示。返回顶部可以和阅读百分比合并为一个轻量按钮，避免右侧出现多个浮动控件。

#### 文章元信息和系列

建议显示日期、文章类型、阅读时间、论文数量和更新时间。论文周报按期号独立成文，使用上一篇 / 下一篇和专题入口导航；教程、综述或 Agent 长主题再考虑 Subposts 连续阅读。

#### 文章内容块

论文周报可以固定为：本期概览、研究问题、核心方法、主要结果、个人理解、局限、横向比较和参考文献。固定结构比维护大量 tag 更容易形成稳定阅读习惯。

### 5.3 媒体与 Markdown

#### LaTeX

| 方案 | 特点 | 适用情况 |
| --- | --- | --- |
| KaTeX（`remark-math` + `rehype-katex`） | 快、成熟、教程和插件多 | AstroPaper、Axi、Fuwari 路线；论文常见公式优先选它 |
| MathJax | LaTeX 兼容范围更宽，运行和体积更重 | 大量复杂宏或已有 MathJax 笔记时使用 |
| Temml + MathML | 输出浏览器原生 MathML，erudite v2 默认采用 | 想跟随 erudite v2、重视语义和可访问性时使用 |

建议保持 Markdown 公式语法不变，只替换渲染管线。当前内容以常规论文公式为主时，KaTeX 是迁移风险最低的方案；若选择 erudite v2，先用 Temml 渲染真实笔记，再决定是否需要换回 KaTeX。公式相关的增强优先级是横向溢出、编号与引用、复制 LaTeX，而不是为每个公式增加复杂工具栏。

#### Markdown 与 MDX

remark / rehype 生态最成熟，可以组合 `remark-math`、`remark-gfm`、`rehype-katex`、`rehype-callouts` 和外链处理。Sätteri 是 Astro 新版和 erudite v2 的方向，但旧 unified 插件不能全部直接照搬。

建议普通文章使用 Markdown，需要图表、参数控件或 Tabs 的文章再使用 MDX。MDX 允许在正文中写入 React island，但会增加构建链和升级耦合，不应让所有文章都依赖它。

#### 图片

论文图片至少需要响应式宽度、`alt`、图注、来源和窄屏查看。单图适合 `medium-zoom`；多图、触屏滑动、键盘导航和缩放适合 PhotoSwipe；Mizuki 的 Image Grid / Fancybox 可作为图组体验参考。不要同时引入多个灯箱库。

#### 表格

基础表格用 CSS 横向滚动即可，必须处理窄屏、数字对齐、表头和说明。排序、筛选、固定列等增强只在实验数据量较大时使用，论文正文中的普通对比表不需要默认变成数据应用。

#### 代码块

优先使用 Expressive Code + Shiki。它可以提供语法高亮、文件名、行号、重点行、差异标记、折叠和复制按钮。`rehype-pretty-code` 也可以作为较轻的组合方案。论文笔记中最有价值的是突出新增行、配置文件名和关键实现，不是装饰性窗口。

#### Mermaid 与内容组件

Mermaid 可以在构建时生成 SVG，也可以在浏览器中渲染。构建时生成更适合稳定展示、打印和搜索；浏览器渲染更方便修改，但会增加加载和主题切换处理。普通流程图建议构建时生成，需要查看大图时提供放大。

Callout、Tabs、Steps、Spoiler 和 Quote 对论文笔记有实际价值。建议控制在 `Note`、`Warning`、`Result`、`Limitation`、`Proof`、`Implementation` 六类以内，避免不同主题分别引入一套颜色和组件语义。

### 5.4 交互与发现

#### 搜索

Pagefind 在构建时生成静态索引，不需要服务器，适合 GitHub Pages。Algolia 的搜索、纠错和分析能力更强，但依赖外部服务；Fuse.js 更灵活，但需要自己维护索引。本站先用 Pagefind，文章量和搜索需求明显增长后再评估 Algolia。

#### 归档、专题和相关推荐

周报适合按年份、月份和期号归档，专题入口承担 Agent / 论文周报等长期方向。相关推荐优先按专题生成，重点文章再通过 frontmatter 手动覆盖；不建议一开始做全文相似度推荐。

#### 页面切换

Astro View Transitions / ClientRouter 可以提供页面淡入淡出和共享元素动画，但会改变导航生命周期，目录、灯箱和图表脚本需要重新初始化。它的收益低于目录、搜索和图片放大，建议第二阶段再接入。

#### React islands

Astro 可以让正文保持静态，只激活需要交互的组件：`client:load` 适合首屏图表，`client:visible` 适合正文中后段图表，`client:idle` 适合较重模拟器，`client:only` 适合完全依赖浏览器的组件。Off by One 的图表就是 Astro + MDX + React island 的具体案例。

#### 图表

| 方案 | 适合内容 | 取舍 |
| --- | --- | --- |
| React + SVG | 机制图、方法结构、参数解释、小型模拟 | 可控、清晰、适合嵌入正文，但坐标和交互需自己维护 |
| ECharts | 折线、柱状、热力图、大量 tooltip 和缩放 | 功能完整，但体积和主题适配成本更高 |
| Observable Plot / Vega-Lite | 声明式统计图和可重复数据映射 | 数据表达清晰，复杂交互仍需额外代码 |
| Canvas / WebGL | 大量点、高密度热力图 | 性能好，但可访问性、打印和语义结构较弱 |

论文机制图优先用 SVG；常规实验数据图再选成熟图表库；静态论文结果尽量在构建时生成 SVG / PNG。交互应解释正文中的一个论点，不要把每篇文章都做成完整分析应用。

#### 评论和外部服务

giscus 适合 GitHub Pages，但评论数据由 GitHub Discussions 和外部服务提供。评论属于后续增强，不应影响主题的第一轮选择。

## 7. Off by One 图表案例

指定文章使用 Astro + MDX + React + TypeScript + SVG。`DayDetailEmbed` 是时间轴，`DaysGridEmbed` 是 100 天模拟网格，`FocusBlocksHeatmapEmbed` 是带阈值切换的热力图；组件通过 `client:load` 激活，代码使用 `useState`、`useMemo`、固定 seed 和独立模拟逻辑。作者没有用 ECharts、Chart.js、Recharts 或 D3 绘制这组图。[^off-article][^off-components]

作者公开了[嵌入指南](https://github.com/cduruk/offbyone/blob/09df1f3e4a0825b925ac88061cef623d0aee8301/src/components/poisson-interrupt/ASTRO_EMBEDDING_GUIDE.md)。可复用单位包括组件、模拟逻辑、UI 原语和 CSS，不是复制一个 `.tsx` 文件。图表代码继承 MIT；文章正文和图片另属作者内容。[^off-license]

对论文周报，优先把交互放在解释论点的位置：切换 benchmark / 指标、方法图前后对照、一个参数的解释性模拟、附录或代码折叠。图表交互属于内容组件，主题只提供文章容器和样式约束。

## 8. 论文周报选型

| 优先级 | 选择 | 适用原因 | 主要风险 |
| --- | --- | --- | --- |
| 1 | AstroPaper | 社区和维护信号强，MDX 与基础阅读体验完整 | 论文卡片、图片灯箱和图表需要补充 |
| 2 | astro-erudite | 最接近 nightxade / Off by One，长文和系列能力明确 | v2 默认移除 MDX / React，需要验证接回交互 |
| 3 | Axi Theme | 合集、论文卡片、目录进度、KaTeX 和图片放大直接可用 | stars 少，维护依赖作者 |
| 4 | Astro Theme Pure | 成熟内容组件多，适合局部移植 | UnoCSS 依赖和整体样式迁移成本 |

选择后，用同一篇真实周报验证中文英文混排、长公式、图注、多图、宽表、代码、手机布局、明暗模式、搜索和 JavaScript 未启用时的正文可读性。完成这一步前不锁定迁移方案。
