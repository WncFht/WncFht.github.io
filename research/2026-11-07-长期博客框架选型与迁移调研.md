# 长期博客框架选型与迁移调研

调研日期：2026-11-07。目标是长期维护个人博客、论文笔记、Agent 专题、论文周报与 Publications，优先使用成熟主题和组件，减少自行设计页面。本文重新评估框架选择，不把“保留 Docusaurus”作为前提，也不执行迁移。

Astro 专项补充：[Astro 生态、主题与个人站点总览](./2026-11-08-Astro生态、主题与个人站点总览.md)，包含版本方向、主题维护信号、个人站点归属、交互组件和 GitHub Pages 部署配置。

## 1. 结论与推荐顺序

**不必保留 Docusaurus。针对当前需求，我推荐把 Astro 加成熟博客主题作为第一选择，Hugo 加成熟主题作为第二选择。** Docusaurus 在已有文档站上继续演进仍合理，但本站并没有大量已发布文档、多个文档版本或多语言内容，这些优势尚未成为必须保留它的原因。

这个判断修正了[上一篇视觉调研](./2026-11-07-博客视觉改版参考与复用清单.md)中“保留现框架时优先参考愧怍”的建议范围。上一篇是在减少迁移工作的条件下比较视觉复用；若按未来多年写博客的目标重新选型，我会优先考虑 Astro。

| 面向你的目标的顺序 | 方案 | 主要理由 | 需要接受的代价 |
| --- | --- | --- | --- |
| 1 | Astro + 成熟博客主题 | 与你喜欢的 Axi 等设计来源接近；内容型网站定位；可保留 Markdown、MDX 和 React 扩展 | 主题更新质量差异较大；仍需维护 Node、框架和主题依赖 |
| 2 | Hugo + PaperMod / Stack / FixIt 稳定版本 | 博客主题体系成熟；常规写作与静态构建路径直接；适合减少日常前端维护 | 复杂 React 组件不能直接搬；要学习模板与 shortcode，主题也有版本要求 |
| 3 | Docusaurus + 同框架成熟设计 | 当前功能齐全，内容无需迁移；文档、博客、搜索、目录可以继续使用 | 博客视觉更依赖主题定制；大量覆盖内部组件会增加升级工作 |
| 4 | Next.js + 完整博客模板 | React 应用能力强；未来如果发展为交互产品，有完整扩展路线 | 内容管线、静态导出和服务端能力需要更多工程判断，不符合“尽量少自己写”的首要目标 |
| 条件选项 | Hexo / Jekyll / Quartz / VitePress / Ghost / WordPress | 各有明确优势，适合特定写作方式 | 是否合适由主题偏好、笔记组织和编辑方式决定，详见后文 |

这不是通用排行榜。若未来主要发布带多个版本的开源项目文档，Docusaurus 的优先级会升高；若主要公开 Obsidian 知识库，Quartz 会升高；若需要多人编辑、会员和邮件订阅，Ghost 或 WordPress 才应进入主选。

## 2. “上限更高”和“资源更丰富”需要分开看

### 2.1 对博客有意义的上限

普通文章、长文目录、LaTeX、图片灯箱、宽表、代码、Mermaid、专题、搜索、评论和 RSS，在多个候选中都能实现。它们不足以证明某个框架有独占的技术上限。

| 上限的含义 | 对博客真正有帮助的判断 | 对选型的影响 |
| --- | --- | --- |
| 视觉自由 | 有多少完整、适合自己的主题；是否容易保留原主题效果 | Astro、Hugo、Hexo、Jekyll 都应按具体主题比较 |
| 内容表现 | 公式、图、表、代码、嵌入组件能否一致呈现 | 依赖渲染管线和主题整合，不只看框架名称 |
| 应用能力 | 登录、个人数据、交互实验、服务端 API、复杂状态 | Next.js 等应用框架更值得考虑；纯博客未必需要 |
| 内容体量 | 大量文章、资源、搜索索引和构建能否持续维护 | 需要实际数据测量；不凭品牌给构建速度排名 |
| 长期维护 | 主题如何升级，覆盖了多少文件，内容是否容易移走 | 比一次性实现的功能数量更重要 |
| 编辑发布 | 是否需要浏览器编辑、多作者、审核与订阅 | 静态生成器与 CMS 是不同工作方式 |

公式是否漂亮，主要取决于 KaTeX / MathJax 的配置、数学字体、字号、行间距、溢出处理和主题排版。换成 Astro 或 Hugo 后不会自动获得更好的公式。类似地，中文字体子集、图片尺寸和图表加载也不会仅因框架改变就自动优化。

### 2.2 生态至少有五种

| 生态类型 | 应查什么 | 对本站的价值 |
| --- | --- | --- |
| 框架与工具 | 文档、构建、部署、测试、图像和 UI 库 | 决定能否继续扩展 |
| 成熟博客主题 | 文章、列表、归档、目录、搜索、暗色是否是一套成品 | 对“不要自己设计”最直接 |
| 中文使用资料 | 中文文档、实际使用者、问题讨论、第三方扩展 | 帮助长期排错和修改配置 |
| 学术内容资源 | 数学、论文图表、引用、Publications、长文示例 | 要看真实示例，而非只有支持清单 |
| 上游维护机制 | release、迁移文档、主题包、配置覆盖与 fork 更新 | 决定两年后改一次是否仍可控 |

React 库可以服务 Astro 的 React 岛，也能服务 Docusaurus 和 Next.js，前提是处理对应上下文与构建限制。因此“想复用 React 组件”不要求选择 Next.js。反过来，Next.js 的大量应用教程也不能直接替代一套适合论文阅读的博客主题。

本文不以 GitHub stars、主题总数或 npm 下载量直接证明生态适合程度。官方目录只能确认资源入口存在；某主题功能由 README 或源码确认，也不代表所有功能都在浏览器中逐项验收。

## 3. 核心框架对比

| 维度 | Docusaurus | Astro | Hugo | Next.js |
| --- | --- | --- | --- | --- |
| 定位 | 文档网站，内置博客能力 | 内容型网站，也支持动态能力 | 静态内容生成 | React 应用框架 |
| 常规写作 | Markdown / MDX | Markdown / MDX；Content Collections 管理内容 | Markdown；模板与 shortcode 扩展 | MDX 等方案需配内容读取、元数据和路由 |
| 成品设计选择 | 官方文档主题与社区定制站 | 官方主题目录，个人博客模板选择直接 | 官方主题目录，博客主题是主要资源之一 | 有完整 starter，但不能把所有 UI 组件当成博客主题 |
| 内容外的 React | 原生 React 体系 | 官方 React 集成，按需加入交互岛 | 需要额外构建与挂载，不是原生内容组件方式 | 原生 React 体系 |
| 文章目录与组织 | 文档侧栏、博客归档等现成；专题可自定义 | 路由与内容查询灵活；专题页面依主题或少量适配 | section、taxonomy、菜单与模板 | 由模板或自建内容层提供 |
| 默认前端思路 | React 网站与客户端路由 | 大部分内容生成 HTML，交互显式加载 | 静态 HTML，主题按需加脚本 | Server / Client Components；静态、服务端按部署方案配置 |
| GitHub Pages | 已支持，本站正在使用 | 支持静态部署 | 支持静态部署 | 支持 static export，部分服务端功能不可用 |
| 主要升级成本 | 框架、主题 API、swizzle 覆盖 | Astro、集成、主题代码和内容处理器 | Hugo 版本、主题模板与资源工具链 | Next.js、React、内容层及相关插件 |
| 本站适配判断 | 可继续，但不必因现状锁定 | 综合最匹配 | 更注重少维护时优先 | 有明确应用需求再优先 |

定位与部署判断分别依据各框架官方资料。[^docusaurus-blog][^astro-why][^astro-islands][^astro-collections][^hugo-content][^next-mdx][^next-export][^astro-deploy][^hugo-deploy]

### 3.1 Docusaurus：保留它的条件已经发生变化

Docusaurus 并非只能写文档。官方支持 blog-only 模式，可以让博客列表成为首页；也支持 React 页面、CSS 定制和主题组件覆盖。正文、论文、合集页不存在技术上做不到的障碍。[^docusaurus-blog][^docusaurus-style]

它最有价值的现成能力包括文档导航、版本管理、翻译与文档博客共存。对于要维护多版 SDK、课程或产品手册的网站，这些能力能减少大量工作。版本管理也会复制内容并增加后续维护，官方明确提示要考虑实际需要。[^docusaurus-version]

本站目前只启用中文，没有维护多版文档；Agent、论文周报和 Publications 更像个人内容站。为了这些功能不断增加主题覆盖，可能会让现成文档框架的收益被定制成本抵消。这是针对当前仓库的判断，不是 Docusaurus 缺少扩展能力。

如果最终选择保留，应优先沿用愧怍这类同框架成品结构，控制 swizzle 范围，并把注意力转回写作。若最终想直接使用 Axi 或 AstroPaper，长期转换别的框架主题反而不如选择其原生框架。

### 3.2 Astro：最符合当前长期方向

Astro 官方明确面向博客等内容型网站。其岛屿架构让静态正文主要输出为 HTML，交互组件使用 `client:*` 指令按需要加载；官方也提供 React 集成。可以继续使用 React 写复杂小组件，不必把整站都变成 React 应用。[^astro-why][^astro-islands][^astro-react]

Content Collections 可以为本地或外部内容定义 loader 和 schema，查询并生成文章页面。对本站，可以统一组织文章、论文笔记和周报的元信息，再按专题生成入口；当前自定义插件中读取两套 Docusaurus 元数据的逻辑可以简化为原生内容查询。这里是架构适配建议，尚未写迁移实现。[^astro-collections]

Astro 也有官方主题目录和集成目录。此前研究的 Axi、AstroPaper、Fuwari、Koharu、Bokushi 和潮流周刊都提供了可读的 Astro 实现，直接使用这些主题通常比持续翻译成 Docusaurus 组件更接近原设计。[^astro-themes][^astro-integrations][^visual-research]

它的代价不能省略：

- Astro 不是一个自带所有博客功能的固定主题。归档、搜索、目录、数学、Mermaid、图注、评论、系列导航需要看所选主题是否已经整合。
- 很多主题实际是 fork 后维护的起始仓库，更新方式是比较源码，而非升级一个主题包。改动越多，合并上游越费力。
- React 岛之间不自动共享一个 React 根上下文；依赖路由或 Provider 的现有组件需要适配。
- 默认少加载 JavaScript 不等于任何主题都轻量。大字体、封面、动画、搜索和图表仍可能成为成本，必须测量。

**Astro 的推荐理由是适合内容、方便采用你喜欢的主题，同时保留扩展空间；不是承诺它不需要维护。**

### 3.3 Astro 当前版本差异必须单独处理

读取的主题源码版本如下，不能把它们当作同一代模板直接混用。

| 主题快照 | `package.json` 中的 Astro | 对采用方式的影响 |
| --- | --- | --- |
| Axi Theme | `5.16.8` | 喜欢其外观仍然合理，但新站采用前要检查当前稳定版本、升级路线与集成兼容 |
| Fuwari | `5.13.10` | 同样要检查主题与目标框架版本的兼容，不能仅看预览图 |
| AstroPaper | `^7.4.5` | 与当前新文档更接近，但主分支不自动等于最适合采用的稳定 release |

来源为对应仓库的固定提交。[^axi-package][^fuwari-package][^paper-package]

Astro 7 官方升级文档说明，默认 Markdown 管线已改为 Sätteri；旧的 remark / rehype 管线可以通过安装 `@astrojs/markdown-remark` 并选择 `unified()` 继续使用。MDX 的处理器也可以配置。本站的 `remark-math`、`rehype-katex`、自定义图片转换不能不加检查地复制旧版教程配置。[^astro-v7][^astro-mdx]

因此，应先选定受支持的框架与主题版本组合，再验证数学、图注、代码和 Mermaid。需要保留现有 remark 插件时，可以明确采用官方提供的 unified 兼容路线；不必为了框架升级同时重写所有内容插件。

### 3.4 Hugo：长期写作与少维护的强候选

Hugo 的静态内容生成、主题、菜单、分类和资源管理形成了成熟工作方式，官方提供主题目录。常规内容可以留在 Markdown，通过主题参数控制展示；数学和 Mermaid 有官方文档中的配置与 render hook 路线。[^hugo-content][^hugo-themes][^hugo-math][^hugo-diagrams]

最适合本站比较的三个主题如下。

| 主题 | 风格与成品能力 | 许可证 | 采用时检查 |
| --- | --- | --- | --- |
| PaperMod | 文字型、简洁；阅读时长、目录、归档、Fuse.js 搜索、复制、明暗模式 | MIT | 数学与 Mermaid 的实际接入；目录形态是否满足长文需求 |
| Stack | 卡片与侧栏；目录、搜索、PhotoSwipe、暗色 | GPL-3.0-only | 图片与论文长文的效果；保留许可和声明 |
| FixIt | 配置与扩展较多；公式、Mermaid、Tabs、提示块、ECharts 等 | MIT | 选稳定版本；当前主分支明确处于下一大版本开发阶段 |

源码和官方演示见对应来源。[^papermod][^stack][^fixit]

Hugo 通常可以减少 Node 依赖，但这取决于主题。PaperMod 当前 README 明确列出无需 JavaScript 构建依赖；Stack 带 TypeScript 资源与样式工具，不能把所有 Hugo 主题概括为“只装一个二进制，永久不用管”。主题也有最低 Hugo 版本，例如读取的 PaperMod 和 Stack 分别声明 0.158.0 和 0.157.0。[^papermod][^stack]

Hugo Modules 支持管理主题与组件依赖，适合保持主题来源与站点配置分离。大量覆盖布局仍会增加升级工作，与其他框架一样。[^hugo-modules]

它的主要短板是交互组件的开发方式。普通图表、搜索和灯箱并不困难；但若未来想在文章里反复嵌入 React 实验、模型演示、可交互参数面板，Astro 比 Hugo 更方便。Hugo 的 shortcode 也会成为内容格式的一部分，过多使用会增加下一次迁移成本。

**如果你的想法是“选好一套主题，然后主要写 Markdown，偶尔改参数”，Hugo 完全可以排在 Astro 前面。**

### 3.5 Next.js：应用扩展能力强，但不应仅因名气迁移

Next.js 官方提供 MDX 集成与静态导出能力。它适合未来把网站发展成交互应用、用户系统或具有服务端数据的产品，同时继续使用 React 生态。[^next-mdx][^next-export]

但 Next.js 本身没有替你决定文章 schema、专题、RSS、归档、搜索和阅读样式。直接新建项目后，仍要搭建这些内容能力；选择完整模板才符合“尽量复用成品”的要求。

核查的 `timlrx/tailwind-nextjs-starter-blog` 是一个可比较的完整起点：有文章布局、数学、代码、搜索、订阅与评论等集成。实际依赖是 Next 15.5.12、React 19.2.4、Tailwind 4 和 `contentlayer2`，而 README 的部分说明仍写 Tailwind 3 和泛称 Contentlayer。依赖事实应以固定快照的 `package.json` 与配置为准。[^nextblog]

这个例子也说明长期成本：框架、React、MDX、内容层和模板需要一起兼容，模板作者是否跟进非常重要。不能因为某个 starter 的历史表现好，就承诺它未来自动跟进框架主版本。官方有专门的升级文档，采用者仍要执行升级和验证。[^next-upgrade]

当前 GitHub Pages 只能托管静态产物。Next.js static export 可以部署，但默认图片优化、Server Actions、依赖请求的动态路由、cookies 等服务端能力不能直接使用；如需这些能力，要另选运行环境或外部服务。被静态化的 React Server Components 可以在构建时运行，因此也不能说 static export 完全不能使用 Server Components。[^next-export]

读取的模板配置确实支持通过 `EXPORT` 启用导出、通过 `UNOPTIMIZED` 调整图片。这不表示订阅 API、安全响应头或所有服务端功能在 GitHub Pages 上原样有效；需要按部署目标取舍。[^nextblog-config]

另外，读取时该模板 README 链接的演示返回 HTTP 402，不能将其视作当前已验证可用的视觉样板。源码仍可评估；短时访问状态也不足以断言项目停止维护。

## 4. 其他框架是否值得考虑

### 4.1 Hexo：中文博客主题与配置资料值得认真考虑

Hexo 有官方主题和插件目录。Fluid、Butterfly 等主题带中文文档，并已经整合数学、Mermaid、搜索、代码工具、图片查看、评论等常见博客能力。这条路线很适合喜欢某个成品主题、希望主要修改配置的人。[^hexo-themes][^hexo-plugins][^fluid][^butterfly]

| 主题 | 已核实特点 | 对本站的判断 |
| --- | --- | --- |
| Fluid | Material Design 风格；本地搜索、脚注、LaTeX、Mermaid；独立站点主题配置 | 如果认可其整篇文章的视觉，可列入最终试用 |
| Butterfly | 多种代码工具、数学、图表、图片灯箱、系列、评论与装饰选项 | 功能选择多；必须关闭不需要的装饰，不能把“全部开启”当作美化 |

Fluid 根许可证为 GPL-3.0，Butterfly 为 Apache-2.0。源码与版本快照列在文末。

我没有把 Hexo 排在主选前两名，原因是你已有 React 扩展需求，并明确喜欢 Axi 一类 Astro 设计，而非 Hexo 不能长期使用。若看过 Fluid 或 Butterfly 后明确更喜欢它们，完整采用主题比在 Astro 中重新仿制一遍更合理。Node 工具链也需要维护，不能把主题参数丰富等同于零维护。

### 4.2 Jekyll：成熟技术博客和学术主页仍是有效选择

Jekyll 有 gem 主题、布局覆盖和插件机制。Chirpy 是针对技术写作的完整主题，README 列出公式、Mermaid、搜索、目录和暗色能力；al-folio 提供更明确的学术展示。两者都比“拿一个裸框架自己组装”更接近你的诉求。[^jekyll-themes][^jekyll-plugins][^chirpy][^alfolio]

适合选定成品视觉、主要长期写作的人。代价是 Ruby / Bundler / gem 依赖，以及 Liquid 模板体系。若继续大量嵌入 React 组件，需要独立处理前端构建。

GitHub Pages 默认支持 Jekyll 不代表其托管构建允许所有插件。官方文档说明支持插件有限；需要自定义插件时可以使用 GitHub Actions 自己构建再发布静态产物。本站已经采用 Actions，因此部署到 Pages 不要求选择 Jekyll。[^jekyll-pages]

### 4.3 Quartz：公开知识库比传统博客更合适

当前官方站点为 Quartz 5。它面向数字花园和笔记发布，提供 Obsidian 兼容、双链、反向链接、关系图、全文搜索、预览、数学和 Mermaid 等功能。[^quartz][^quartz-features]

如果未来主要工作方式是“在 Obsidian 写大量互相链接的笔记，并把选定内容公开”，Quartz 值得单独试用。若重点是精选论文文章、周报、个人主页和 Publications，其知识库式默认信息结构未必最符合访客阅读顺序；这取决于内容组织，不是技术能力差异。

读取的仓库 `package.json` 为 5.0.0，配置与插件组织已经变化。旧的 Quartz 4 教程不能自动套用于当前版本。不要仅因有关系图就增加一套长期维护的网站。[^quartz-repo]

### 4.4 VitePress / Starlight / Fumadocs：仍需判断是不是在做文档站

VitePress 官方定位为内容型静态生成器，默认主题用于技术文档，也支持博客和自定义布局；其 `createContentLoader` 可生成文章索引。因此它能写博客，但博客页面仍要选成熟主题或自行实现。当前 React 组件也需要转换为 Vue 或独立挂载。[^vitepress][^vitepress-data]

Starlight 是 Astro 文档主题，Fumadocs 是面向多种 React 框架与 Astro 的文档方案。它们的内容组件有完整设计，但如果不需要版本化文档、页面树和文档布局，换到另一套文档主题不一定解决“更像个人博客”的诉求。应作为偏好文档风格时的选项，而不是默认的博客升级路线。[^visual-research]

### 4.5 Ghost / WordPress：改变的是编辑与运行方式

Ghost 和 WordPress 提供浏览器编辑、多作者和插件 / 主题生态，更适合不希望通过 Git 提交文章，或者需要订阅、会员、编辑协作的网站。[^ghost][^wordpress]

它们属于 CMS 路线。常规自托管运行需要后端环境与数据库；托管服务可以减少运维，但会改变费用、数据备份与服务依赖。不能直接放到 GitHub Pages 就获得完整 CMS 功能。Ghost 官方自托管说明明确包含 Node、数据库与服务器要求。[^ghost-host]

对于目前的本地 Markdown、论文笔记和 Git 工作流，我不优先推荐这条路线；如果以后写作方式改变，再重新评估。已有大量主题和插件，并不代表复杂数学、代码与论文图表无需检查就能获得理想效果。

## 6. 当前仓库的迁移成本

### 6.1 内容少，定制代码已经不少

仓库检查结果：`docs` 和 `blog` 中有 4 个 Markdown / MDX 文件，其中 2 个是实际文章，另外 2 个是入口与实验页。实际文章之一是尚未提交的 MOPD 论文笔记；它有 564 行、72 个标题，没有检出的自定义大写 MDX 组件标签。这里的标签检查只是简单文本统计，不等于已证明所有语法能无修改迁移。

`src` 中有 40 个 TS / TSX 文件，其中 22 个直接引用 `@docusaurus` 或 `@theme`；`src/theme` 有 13 个 TSX 覆盖文件。迁移的主要成本已经是代码和行为，而非搬运大量历史文章。这些数字来自当前工作区，不是框架通用指标。

| 当前资产 | 迁移到 Astro | 迁移到 Hugo |
| --- | --- | --- |
| Markdown 正文、图片原文件 | 大部分可沿用，验证扩展语法 | 大部分可沿用，检查渲染差异 |
| 数学公式、表格、代码、Mermaid 源码 | 保留内容，接入选定主题的渲染管线 | 保留内容，按主题或 render hook 配置 |
| `collections`、`issue`、`series_order` 等元数据 | 定义 schema，映射到内容查询和专题页面 | 映射为参数、taxonomy 或专题模板，验证顺序 |
| `sidebar_*`、`last_update`、TOC 层级字段 | 转换、移除或兼容 | 转换为目标主题支持的字段 |
| 字体文件与颜色角色 | 可以复用资源和语义定义，重新映射主题 | 可以复用资源和变量，适配主题 CSS |
| React 卡片等组件 | 可保留部分逻辑；替换 Link、Heading 与内容上下文 | 优先用主题原生模板；复杂组件需独立接入 |
| Docusaurus 主题覆盖 | 大部分放弃或参考行为重接 | 大部分放弃或用主题能力替代 |
| 当前内容目录插件 | 改为 Astro Content Collections 和静态页面生成 | 改为 Hugo 内容查询、分类和模板 |
| easyops 搜索 | 不能原样沿用；选主题原有搜索或静态搜索方案 | 使用主题搜索或适配静态搜索 |
| GitHub Pages 与域名 | 可继续，修改构建和产物上传 | 可继续，修改构建和产物上传 |

Astro 的 Content Collection 是框架的内容集合概念，本站 front matter 的 `collections` 是文章所属专题字段，两者名称相近但不是同一接口。迁移时可以保留专题字段，再用它生成页面。

既然用户已经否定上一版外观，没有必要为了保留这些组件而继续锁定框架，也没有必要把它们全部搬到新框架。优先采用新主题现成实现；真正值得保留的是内容、路径、字体偏好和确有需要的行为。

### 6.2 URL 比目录位置更需要保护

当前站点配置是用户级 GitHub Pages、根路径 `/`、不统一追加末尾斜线。需要记录的路径包括：

- `/blog` 及各文章路径，当前文章通常由日期和文件名生成，需要从构建产物核实实际 permalink。
- `/docs/intro`，以及 MOPD front matter 指定、位于 docs 路由下的 `/docs/papers/mopd`。
- `/collections`、`/collections/agent`、`/collections/paper-weekly`。
- RSS / Atom、站点地图、图片地址、标题锚点，以及文章之间的链接。

最稳妥的迁移方式是先保留公开 URL；若确需修改再准备映射。GitHub Pages 不能按常规服务器方式随意配置 HTTP 重定向，生成旧路径页面只是兼容办法，不应统称为服务器 301。相同 Markdown 标题在不同渲染器中生成的锚点也可能不同，长文已有引用要核对。

MOPD 是未提交的本地文章，这里只检查迁移兼容，不将它加入提交或发布。

### 6.3 搜索、图表与性能需要单独验收

Pagefind 是可用于静态站点的选择：在站点生成后建立索引，并提供成品搜索 UI，不要求为搜索运行后端。它可以被不同静态框架采用，不能视为 Astro 独有。中文检索质量、数学源码过滤、页内命中和搜索加载成本仍需用本站真实文章测试。[^pagefind]

性能比较至少要使用同一篇长文、相同图片和字体，在构建后的桌面与手机环境测量。本文没有对这些主题做可比构建基准，因此不给出“快几倍”、固定首屏体积或 Lighthouse 分数排名。Astro 的显式岛屿加载与 Hugo 的静态输出是架构事实，不能代替具体主题的实际测量。

## 7. 长期使用时怎样减少再次迁移的成本

| 维护策略 | 具体做法 | 原因 |
| --- | --- | --- |
| 正文保持可迁移 | 普通 Markdown 优先；复杂组件限于少量页面；记录扩展语法 | 主题可以更换，文章不应依赖大量专属组件 |
| 统一元数据 | 标题、描述、日期、更新日期、专题、可选论文来源定义明确 | 专题页与 RSS 不再各写一套临时规则 |
| 显式 URL | 重要文章记录稳定路径，迁移前导出路径映射 | 减少外链和收藏失效 |
| 控制主题差异 | 用主题配置和少量扩展，修改范围有记录 | 降低合并上游成本 |
| 分开内容与外观 | 主题图标、装饰和交互不写入普通文章正文 | 减少换主题时清理文章的工作 |
| 固定可复现版本 | 保存 lockfile、运行时版本、主题来源与提交 | 旧站可重建；框架大版本升级有独立验证 |
| 保留渲染样例 | 一篇同时含公式、图、表、代码、目录和图表的实验页 | 每次更新都能检查实际影响 |
| 静态部署优先 | 没有明确动态需求时不引入数据库和常驻服务 | 保持本地写作、Git、构建与托管流程直接 |

静态站可以长期展示，但没有框架能保证未来十年不维护。长期可靠性更依赖内容格式、主题改动规模、依赖可复现和升级节奏。

## 8. 针对本站的最终建议

**我建议允许更换框架，并把 Astro 作为下一轮成品试用的默认方向。** 优先比较 Axi 与 AstroPaper：前者最符合已经表达的审美偏好，后者可作为简洁长文方向的对照。决定时要同时评估主题外观和目标版本的维护状况，不只看首页截图。

**如果你希望后续尽量只写 Markdown，愿意牺牲一部分 React 小组件的便利，就把 Hugo 的 PaperMod / Stack 同时列入最终候选。** 它们提供了另一种长期使用取舍，不能只因采用不同语言而排除。

Next.js 暂不作为优先迁移目标。等出现登录、用户数据、复杂互动或服务端产品功能等明确需求，再考虑其应用能力；届时博客也可以与独立应用并存，不必现在为了未知需求把整个博客做成应用工程。

实际迁移前应做小范围、可丢弃的同文比较：用相同的公开示例文章，在选定的 Astro 主题与一个 Hugo 主题中生成正文页、专题页和手机版目录。使用主题原有组件，评估视觉、写作、构建、升级和路径保持，再决定整站切换。当前没有启动这些原型，也没有变更生产站。
